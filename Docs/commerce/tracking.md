### ORD-02 evidence — reservation expiry and low-stock (2026-10-18)

- **Reservation expiry (consumer-driven, no scanner).** Design choice: the `reserve()` path already enqueues one durable `reservation_expiry` job per reservation in the same transaction, so instead of a separate cron scanner the job's `available_at` is now set to the reservation `expires_at` (`QueueService::reservationExpiry($id,$now+$ttl)`). This is the guide's "release expired reservations once, idempotently" with the existing durable outbox rather than a bounded-batch scanner; it trades a per-reservation job row for no new scan command or scan-side dedupe. The `maintenance` queue is now enabled (`JobRegistry::enabledQueues()`), and `JobRegistry::execute()` dispatches `reservation_expiry` to the rewritten `ReservationExpiryJob`.
- `ReservationExpiryJob` was previously broken (called the private `reservation()`, never wrapped a transaction, never acknowledged, and had a `!$x === 'sqlite'` precedence bug whose rollback never ran) and was never registered in `config/classes.php`, so it would have fatally failed as an unknown class the first time it ran. It now decodes the envelope, calls the new `InventoryService::expireReservation()` under one transaction, acknowledges the lease on a terminal outcome, and — if claimed before the lease actually expired — throws `reservation_not_expired` so the release is retried rather than dropped.
- `InventoryService::expireReservation()` locks the header, returns `missing`/`closed`/`active` without effect, and only releases (via the existing `close('expired')`) when state is active and `expires_at<=now`; replay on a closed reservation is a no-op.
- **Low-stock alerts, default-off.** New migration `0020_low_stock_alerts.php` adds `low_stock_alerts` and an edge-trigger `inventory.low_stock_notified` flag (declared `INT` so `verifyDefinition` matches on both drivers). `InventoryService::maybeLowStock()` runs after every on-hand-decreasing write (consume, negative adjust) and recovery write (positive adjust, cancellation restock): with `INVENTORY_LOW_STOCK_THRESHOLD_MILLI=0` it is a no-op (so all prior tests are unchanged); above zero it fires one alert per dip to/below the threshold and clears the flag once stock recovers above it. The alert enqueues `low_stock_alert` on the `emails` queue; `NotificationJob` gained a branch that emails `OPS_ALERT_EMAIL` (missing recipient → safe classified failure, retryable), reusing the existing delivery/lease/transport machinery and `notification_deliveries` dedupe.
- Evidence (PHP 8.3.6 / SQLite 3.45.1, from `Website/`): new `tests/ReservationExpiryTest.php` **19 checks** — delayed job created at expiry, unexpired reservation not released early, expired release exactly once with one `expired` movement and job acknowledged, replayed release no-ops, consumed-reservation expiry acknowledges without altering stock, low-stock default-off, single alert per dip with flag set, no re-alert while still low, flag cleared on recovery, fresh alert after recovery, worker delivery with correct SKU subject and distinct sent deliveries, missing-recipient failure without a delivery, and successful delivery after the recipient is configured.
